# 前端开发规范

## 0. 总体规则

以下两条规则适用于本项目所有开发活动，优先级最高：

1. **代码注释规范**：所有代码块（函数、类、复杂逻辑块、配置常量、组件等）必须编写清晰的功能注释说明。
   - 函数/方法注释：说明其用途、关键参数、返回值与副作用；复杂算法需补充实现思路。
   - 组件注释：说明组件职责、Props 含义、状态含义与交互行为。
   - 配置注释：说明配置项的业务含义与取值约定。
   - 注释应随代码同步更新，禁止保留过时、误导性注释；注释使用中文，表达简洁准确，避免复述代码字面含义。

2. **项目说明书维护规范**：项目整体结构与文件说明必须实时反映在项目说明书中（`docs/项目说明书.md`）。
   - 新增、删除、重命名、迁移文件或目录时，必须同步更新项目说明书对应章节。
   - 功能模块、核心配置、公共组件、工具 hooks、service 等变更后，需更新其职责说明。
   - PR/提交前自检说明书是否与实际代码结构一致；说明书与代码不一致视为缺陷。
   - 维护者变更模块结构后，在说明书"维护记录"中追加一行简述（日期 + 变更概要）。

## 1. 技术基线

- 核心：React 19、TypeScript、Vite、Zustand、Ant Design。
- 路由使用 `react-router-dom`；跨页面共享状态使用 Zustand，组件局部状态优先使用 React State。
- 新增依赖须评估包体积、维护状态、许可证和替代方案；禁止未经评审引入大型全量工具库。

## 2. 架构与复杂业务拆解

采用按业务域组织的结构，推荐 `src/features/<domain>/` 下分为 `components`、`hooks`、`services`、`stores`、`types`。页面只负责编排，业务规则放入 hooks 或 services，展示组件保持可复用、可测试。

- 单个组件职责单一；复杂页面按容器、展示、领域逻辑拆分。
- API 调用统一沉淀于 service，明确请求/响应类型、错误边界与取消策略。
- 跨域共享状态最小化，store 按领域拆分；使用 selector 获取必要字段，避免订阅整个 store。
- 对不可靠数据、异步加载和权限缺失提供空态、加载态、错误态及可恢复操作。

## 3. 组件库与体验

优先组合 Ant Design，而不是复制其基础能力。公共业务组件放在 `src/components`，必须定义清晰的 Props 类型、受控/非受控行为和无数据状态。

- 可访问性：使用语义元素、可见焦点、键盘可操作；图标按钮须提供 `aria-label` 或文字。
- 表格和长列表使用分页、虚拟化或按需渲染；交互中的 loading 应防止重复提交。
- 样式采用响应式布局；间距、颜色、圆角等使用设计令牌，禁止页面间随意复制硬编码值。

## 4. 性能准则

- 路由级代码分割，重量级图表、地图和大屏模块采用 `lazy` 动态加载。
- 避免在 render 中进行昂贵计算；仅在有实际收益时使用 `useMemo`、`useCallback`、`React.memo`。
- 图片使用现代格式、明确尺寸和懒加载；首屏关键资源优先，其余资源延后加载。
- 请求需要去重、缓存、超时、取消和失败重试策略；不缓存敏感或易失效数据。
- 使用浏览器 Performance、Lighthouse 与包分析定位瓶颈，不以猜测代替测量。

## 5. 多端与智慧大屏适配

- 以 320px 为最小可用宽度；常规业务采用 Mobile First + CSS Grid/Flex，关键断点至少覆盖 768px、1024px、1440px。
- 大屏采用以设计稿基准尺寸为中心的缩放容器，并限制最小字体、可点击区域和缩放范围；不得将缩放方案直接用于普通业务页面。
- 同一操作在鼠标、触控、键盘下语义一致；触控目标建议不小于 44px，悬浮信息要有点击替代方案。
- 检查横竖屏、不同 DPR、浏览器缩放和安全区域；禁止只根据 UA 识别设备。

## 6. 工程与交付

- Vite 使用手动分包，依赖体积变化时复核 chunk 策略；生产构建保留 source map 以支持排障。
- 提交前运行 `npm run build`（由 Husky pre-commit 钩子自动执行）。
- CI 必须执行安装、静态检查、格式检查、单测和构建；部署以构建产物及版本号为唯一来源。
- Git 仓库初始化后执行 `npx husky init`，并将 `.husky/pre-commit` 配置为 `npx lint-staged`。

## 7. 质量门禁

- TypeScript 禁止使用 `any`；为边界数据编写显式类型和运行时校验。
- 每个新增业务逻辑至少覆盖主路径、异常路径和边界条件；修复缺陷时先补充可复现测试。
- 代码评审关注职责边界、状态一致性、无障碍、性能影响、错误处理和多端表现。
